### AMBER (16)

#### Live chunk upload failures are silent and lossy — the audio is spliced out of the buffer before the fetch

`islands/HomeIsland.tsx:474`

`sendChunk` removes the chunks from `chunksRef` (line 453, `splice(0)`) before
uploading, then only acts on success — there is no `else` on `res.ok`, and the
catch does nothing but `console.error`. Any non-2xx drops that speech
permanently with zero user feedback while the recorder keeps ticking and the
live transcript panel simply stops growing. Concrete triggers: a near-silent
chunk makes the transcription model return empty → openrouter.ts:203 throws
"OpenRouter returned an empty response" → chunk.ts returns 500; the 60/min burst
limit in requestGuard fires (silence-triggered flushes can exceed 20-30/min in a
conversation with pauses, on top of /api/live/analyze); or the 4h
`API_SESSION_TTL_MS` expires mid-meeting — `sendChunk` is the one AI-calling
client path that never calls `ensureApiSession()` (it's only wired to
`onBeforeStart` at line 275), so the 401 is invisible and unrecoverable.

**Fix:** On the non-ok / catch paths, put the audio back and say so:
`chunksRef.current.unshift(...chunks);` plus a one-shot
`showToast("Lost the last few seconds — still listening", "warning")` (throttled
so a dead connection doesn't spam).

#### AI request failures degrade to empty results with no warning, so a half-analysed map is shown as a success

`core/ai/openrouter.ts:338`

`extractActionItems` and `extractTopics` swallow every thrown error into `[]` /
`{nodes:[],edges:[]}` without calling the `onParseError` sink they were handed.
The sink is the only input to `buildWarnings` (parallel-analysis.ts:106), so
`warnings` stays empty for request failures — only JSON _parse_ failures produce
a warning. Concrete case: OpenRouter 500s the action-item call three times
(withRetry exhausted) while topics and summary succeed. `analyzeText` resolves
cleanly, `warnings` is `[]`, and UploadIsland.tsx:217 cheerfully toasts
"Processed! Found 0 action items, 5 topics". The user reads a silently truncated
map as a complete one, and on the append path the same silence means a round
that extracted nothing looks identical to a round where nothing was said.

**Fix:** Call the sink in those two catch blocks —
`onParseError?.("action items")` and `onParseError?.("topic map")` — so a failed
request produces the same user-visible warning a garbled one already does.

#### Live Stop button goes dead during every transcription chunk upload

`islands/HomeIsland.tsx:668`

The host's record/stop button is disabled whenever
`isProcessing && isRecording`, but `sendChunk` sets `isProcessing.value = true`
for the whole duration of each chunk upload (line 455) — and chunks flush on
every 2s of silence or every 30s. So throughout the recording the Stop button is
intermittently unclickable, for the length of a transcription round-trip each
time. On the LLM path (no `DEEPGRAM_API_KEY`) that is a multi-second dead window
per flush; the CLAUDE.md notes the LLM turn is "multi-second" vs Deepgram's
~300ms. A user tapping Stop during an upload gets a button that does nothing,
with the timer still running.

**Fix:** Drop the disable while recording —
`disabled={isProcessing.value && !isRecording.value}` (or remove the condition
entirely). `stopRecording` already flushes the buffer and awaits the in-flight
chunk, so stopping mid-upload is safe.

#### Append result lands on whatever conversation is open when it returns — no id guard before the write

`islands/AudioRecorder.tsx:308`

`processAudioAppend` snapshots `base` at send time and then assigns the
reconciled result straight onto the global signal, with no check that the user
is still on the same conversation. Switching is reachable mid-flight:
MobileHistoryMenu's row click loads another conversation with no processing
guard. Concrete failure: user records a take on conversation A, opens History
and clicks conversation B while the 5-10s append is in flight; on return,
`reconcileAppendResult(base=A, mine=B, theirs=A-result)` merges A's server
nodes/actions/transcript/title against B's current state and writes the hybrid
onto B — which the autosave effect then persists under B's key. AskModule guards
exactly this case
(`if (conversationData.value?.conversation.id !== askedId) return;`); the append
path does not.

**Fix:** Bail before the write, mirroring AskModule:
`if (conversationData.value?.conversation.id !== conversationId) return;`
immediately before line 308 (`conversationId` is already the prop this append
was issued for).

#### Share creation skips ensureApiSession, so an unauthenticated browser silently gets a non-portable link

`core/storage/shareService.ts:329`

`createBestShareLink` POSTs to `/api/share/create` — a `guardRequest`-protected
route — without establishing the auth session, and its only caller
(`ShareButton.handleShare`) doesn't either (contrast `startMeeting`,
ShareButton.tsx:60, which does). With `API_AUTH_TOKEN` set in production, a user
who opens the app, auto-restores a saved conversation from localStorage, and
taps Invite has never authenticated: the request 401s, the catch at line 360
falls back to `createLocalShareLink`, and they get a `local-only` link that
resolves only in their own browser. The auth modal that would have fixed it
never appears; the failure surfaces only as a warning string appended to a "too
large for a portable URL" message, which misdescribes the cause.

**Fix:** `await ensureApiSession();` in ShareButton.handleShare right before
`createBestShareLink` (it's already imported at line 24), matching startMeeting.

#### A failed first process loses the recording: the blob is never persisted and the island remounts empty

`islands/UploadIsland.tsx:181`

`processRecordedAudio` hands the blob straight to `/api/process` and drops it on
failure — no IndexedDB write, no retry affordance. AudioRecorder deliberately
does the opposite ("Persist the take FIRST — the audio must survive a failed AI
pipeline", AudioRecorder.tsx:99), so the very first take, which can be up to 10
minutes, is the one recording with no safety net. It's made worse by unmounting:
HomeIsland hides the hero the moment `processingConversation` flips true (line
831), so UploadIsland is destroyed during the request and a fresh instance
mounts on the error path — `selectedFile` and `lastUploadName` are `useSignal`
(component-scoped) and come back empty, so a staged audio file must be re-picked
too. The module-scoped `textInput` (line 16) exists precisely because of this
remount; the audio state was never given the same treatment.

**Fix:** Hoist `selectedFile` next to `textInput` at module scope, and keep the
recorded blob in a module-level `lastBlob` (or call `saveRecording` before the
fetch, as AudioRecorder does) so the error path can offer the same retry.

#### Live chunk audio is discarded before the request; any failure loses that speech forever, silently

`islands/HomeIsland.tsx:453`

`sendChunk` splices the accumulated blobs out of `chunksRef` first, then POSTs.
If the response is not ok (401 after the 4h session TTL, 429 from the
burst/daily rate limits, 500 from a transcription failure) the `if (res.ok)`
branch is skipped and nothing happens — no retry, no buffer restore, no toast. A
thrown fetch (offline, dropped wifi) only hits `console.error`. Unlike the
append path (take persisted to IndexedDB before the pipeline) and unlike
`liveAnalysis` (which pushes `text` back to the front of `pendingText` on
failure), live chunk audio exists nowhere else: it is never saved to disk. So
one 429 during a meeting = a permanently missing minute of transcript that the
user is never told about, and the topic map/actions silently skip it.

**Fix:** On `!res.ok` or a thrown fetch, put the blobs back at the front of the
buffer (`chunksRef.current.unshift(...chunks)`) so the next flush retries them,
and surface a one-shot toast when a chunk fails.

#### Silence has no flush latch — a pause fires a transcription request every ~500ms

`islands/HomeIsland.tsx:425`

The 200ms monitor flushes whenever `chunksRef` is non-empty AND
`silenceDuration > SILENCE_FLUSH_MS`. Flushing empties `chunksRef` but does not
reset `lastSpeechRef`, so `silenceDuration` keeps growing. The MediaRecorder
timeslice is 500ms, so a new blob lands ~500ms later, the very next tick sees
the condition still true, and it flushes again — roughly 2 requests/second for
as long as the room stays quiet, each one a paid transcription of pure silence.
`chunkStartRef` is reset but that only governs the `chunkAge` leg. Thirty
seconds of quiet at the start of a meeting is ~60 requests, which is exactly the
`API_RATE_LIMIT` default of 60/min — after which /api/live/chunk starts 429ing,
and per the finding above those chunks vanish silently.

**Fix:** Latch the flush: inside the `if`, also set
`lastSpeechRef.current = now;` so a single silence produces a single flush and
the next one needs fresh speech first.

#### Live chunks race: responses are applied in completion order, so the transcript can scramble

`islands/HomeIsland.tsx:429`

`sendChunk()` is invoked from the 200ms interval without `await` and without any
in-flight guard, so several chunk requests can be open at once. Each response
appends to `liveTranscript`, broadcasts via `sendTranscriptChunk`, and feeds
`noteLiveChunk` at the moment it resolves — the chunk id is `Date.now()` at
_response_ time, not send time, so there is nothing to reorder by. With the LLM
transcription path (multi-second) and the silence-flush cadence above, chunk 3
routinely lands before chunk 2: the room's live transcript, the host's
`liveTranscript`, and the `pendingText` buffer that /api/live/analyze analyses
all end up with sentences out of order.

**Fix:** Serialize the sends: keep a module/ref-level promise chain
(`chunkChain = chunkChain.then(() => doSend(chunks))`) so a chunk's result is
only applied after the previous one's, preserving capture order.

#### Only the first live flush carries the container header; later flushes are headerless fragments

`islands/HomeIsland.tsx:453`

With `recorder.start(500)`, MediaRecorder emits the EBML/Segment header (or the
MP4 `ftyp`/`moov` on iOS) only in the FIRST `dataavailable` blob. `sendChunk`
splices every accumulated blob out and never keeps the first one, so the first
flush uploads a valid file and every subsequent flush uploads bare Cluster (or
bare `moof/mdat`) bytes labelled `audio/webm`. Server-side that is undecodable
audio: Deepgram's prerecorded endpoint and the OpenRouter audio path both need
the container header. Combined with the silent-drop finding, the symptom is a
live transcript that produces one good chunk and then quietly stops producing
text while the recording indicator keeps running.

**Fix:** Keep the first blob: stash it in a ref on the first flush and prepend
it to every later chunk blob
(`new Blob([headerRef.current, ...chunks], {type})`). Alternative with no header
bookkeeping: stop and restart the MediaRecorder per chunk so each upload is a
complete file.

#### Append replaces the speaker roster with only the newest take's speakers

`routes/api/append.ts:171`

The append route concatenates the transcript TEXT but leaves
`result.transcript.speakers` as whatever `processAudio` returned for the new
clip alone. The client stores that as the whole conversation's roster. Speaker
colors are assigned by index into that roster, so after a take where only one
person spoke, an earlier speaker that is still all over the transcript text
either disappears from the roster (falling back to a hash color) or shifts index
and changes color. Concretely: take 1 yields `["Speaker1","Speaker2"]`
(watermelon, sky); take 2 yields `["Speaker1"]`; after the append Speaker2's
transcript lines and action-item dots recolor, and the Voices card's speaker
count reads 1. `/api/live/analyze` has the same gap (it passes through only the
union of the latest chunk speakers).

**Fix:** Union the rosters where the transcript is concatenated, preserving
existing order: pass `existingSpeakers` from the client (or parse them out of
`safeExistingTranscript`) and set
`result.transcript.speakers = [...new Set([...existingSpeakers, ...result.transcript.speakers])]`.
Same two lines in routes/api/live/analyze.ts.

#### Live collab worker's sanitizeNode drops node `aliases` — merge memory dies in live rooms

`workers/collab/src/conversationProtocol.ts:218`

The deployed worker's `sanitizeNode` builds a node object with only
`id/label/emoji/color/position`. The two copies it was ported from both preserve
`aliases`, with an explicit warning comment. Failure: in a live room, a user
drags topic A onto topic B (merge). The survivor node carries `aliases: ["A"]`.

copy comes back to everyone (including the merger, via reconnect INIT or a peer

feature silently breaks, but only in live rooms.

**Fix:** Add `aliases?: string[]` to the node type and copy the 8-line
`if (Array.isArray(input.aliases))` block verbatim from
`party/conversationProtocol.ts:243-249`.

#### .history-drawer-panel keeps a backdrop-filter blur(20px) behind a 95%-opaque background, against the app's own stated policy

`static/styles.css:5766`

The drawer panel paints `rgba(255, 252, 248, 0.95)` and then asks the compositor
for `backdrop-filter: blur(20px)` behind it. At 95% opacity the blurred backdrop
contributes 5% of the final pixel — visually near-nil — but the browser must
still rasterize and gaussian-blur the full region behind a 384px-wide,
full-height panel, and it must redo that on every frame of the slide-in/out
transform. The app already made this exact call the other way and documented it:
the header at line 728 explicitly dropped its blur(20px) for a 96%-opaque fill
with the comment "at ~96% opacity the strip reads identically to the old
backdrop-filter blur(20px), minus the per-frame re-blur that made window resizes
chug. Performance mode over graphics mode." The drawer is the same pattern with
the same opacity and did not get the same treatment. The other backdrop-filter
sites are all modal-only (`.reader-backdrop` 3477, `.topic-node-modal-backdrop`
5029, `.topic-map-fullscreen` 5112, `.history-drawer-backdrop` 5759) and are
legitimate. Separately, `.topic-node-detail` (4898, blur 16px) is a panel that
sits over the live force simulation rather than a modal.

**Fix:** Delete lines 5766-5767 (`backdrop-filter` / `-webkit-backdrop-filter`)
from `.history-drawer-panel`, exactly as was done for `.app-header-glass`. The
0.95 background already carries the look.

#### Reconnect flushes the local snapshot BEFORE INIT arbitration, so a stale tab clobbers a room that moved on — and the rev machinery never gets to vote

`signals/liveSync.ts:144`

The outbound effect reads `partyConnected.value`, so it re-runs when the socket

Meanwhile `unsentLocal` can essentially never be set for the case it was written

`if (!partyConnected.value || !data) return;` and bails long before reaching the
`sendConversationUpdate` whose failure sets the flag at :156. Failure scenario:
A's wifi drops; A toggles two action items; meanwhile B renames a topic (room

effect: `if (awaitingInit) { unsentLocal = true; return; }` placed after the
`applyingRemoteUpdate` check and before the send. That makes the existing rev
comparison in `onInit` the single decision point it was designed to be.

`debouncedSave` has one module-global timer slot and clears it unconditionally,
dropping the closure that held the previous conversation's data. The autosave
effect re-arms on every `conversationData` change, and the history drawer
changes it directly. Failure A: user renames an action item in conversation A
(effect schedules a 500ms save), then clicks conversation B in the drawer
(MobileHistoryMenu.tsx:189 `conversationData.value = conv`) — the effect fires
with B, `clearTimeout` kills A's pending write, and the rename exists nowhere.
Failure B is easier to hit: edit, then tap "New" (MobileHistoryMenu.tsx:233
`conversationData.value = null`) — the effect takes the else branch and calls
`cancelPendingSave()`, which is correct for the delete case its comment
describes but throws away the last edit of a conversation that still exists.

**Fix:** Keep the pending payload beside the timer
(`let pendingData: ConversationData | null`). In `debouncedSave`, if
`pendingData` exists and its `conversation.id` differs from the incoming one,
call `saveConversation(pendingData)` synchronously before rescheduling; in
`cancelPendingSave`, flush instead of dropping when the pending id is not the
one being deleted.

### GREEN (2)

#### The join/leave roster isn't cleared when a session ends, so the next room opens with ghosts leaving

`islands/HomeIsland.tsx:362`

`seenUsers` holds the previous room's roster and is only ever written inside the
effect body — which returns early when `session` is null. When a session ends,
`disconnectFromRoom()` sets `remoteUsers.value = []`, the effect re-runs with
the now-null `session` and bails at the guard, leaving `seenUsers.current`
pointing at the old room's members. Failure scenario: host runs a meeting with
Sarah and Dennis, ends it, then starts a second room on another conversation.
The first PRESENCE message arrives with just themselves, the effect diffs it
against the stale roster and fires "Sarah left" and "Dennis left" toasts into a
room they were never in — plus a chime and a "joined" toast for the host's own
avatar.

**Fix:** Reset the baseline instead of bailing:
`if (!session) { seenUsers.current = null; return; }`. (`liveTranscript` at
HomeIsland.tsx:252 has the same stale-across-sessions shape — a
`liveTranscript.value = []` in the session-effect cleanup covers it.)

#### The storage gauge measures one key against the whole 5MB origin budget

`core/storage/localStorage.ts:412`

`getStorageStats` sizes only `project_mapper_conversations` and divides by a
hardcoded 5MB, but that budget is shared with `markdown_outputs` (up to 100 full
documents — exportSnapshots.ts:30 calls them "the biggest blobs this app
writes"), `project_mapper_shares` (whole conversation copies), and one
`promapper-tag-tints:<id>` key per conversation. MobileHistoryMenu.tsx:125
renders this as the user-facing gauge, and its comment says the point is to make
"the 5MB localStorage ceiling observable". Failure: the drawer reads a
reassuring "0.9 MB of 5 MB" while exports have taken 4MB, and the very next
autosave throws QuotaExceededError and toasts "Storage is full" — the gauge and
the error contradict each other in the same session.

**Fix:** Sum the app's own keys (conversations + `markdown_outputs` +
`project_mapper_shares`) instead of just one, or read
`navigator.storage.estimate()` when available.
